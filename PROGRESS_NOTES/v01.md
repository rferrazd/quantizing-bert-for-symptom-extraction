# Version 0.1

## Motivation

Version 0.0 failed primarily due to **extreme label sparsity**:

* ~3,500 distinct labels
* ~10 examples per label
* Strong dominance of the `"O"` class

This caused the model to converge to a trivial solution (predicting `"O"`), regardless of:

* model choice (DistilBERT vs BioBERT)
* freezing vs training all layers

Version 0.1 focuses on **reducing label complexity** so the model can first learn *what a symptom span looks like*, before learning *which specific symptom it is*.

---

## Key Change from v0.0

All training infrastructure remains the same **except for the dataset labels**.

### v0.0 Labels (too sparse)

```
B-SYMPTOM_s0004_NEG
I-SYMPTOM_s0004_NEG
```

### v0.1 Labels (collapsed)

```
B-SYMPTOM_NEG
I-SYMPTOM_NEG
B-SYMPTOM_POS
I-SYMPTOM_POS
O
```

* **Concept IDs are removed**
* Polarity (POS / NEG) is preserved
* BIO structure is preserved

---

## Expected Benefits

* Label count reduced from ~3,500 → **5**
* Each label now has **thousands of examples**
* Strong parameter sharing across all symptom mentions
* Model can meaningfully learn:

  * symptom boundaries
  * negation vs affirmation

This setup aligns better with how transformer-based NER models are typically trained.

---

## Key Observations

* **BioBERT run_2 outperformed all other runs** while requiring less training time than run_0, suggesting improved convergence and possible overfitting or the other BioBERT runs.
* All BioBERT models exhibit **higher recall than precision** at both token and entity levels, indicating a tendency toward over-prediction.
* Performance is **well-balanced between SYMPTOM_POS and SYMPTOM_NEG**, reflecting a balanced dataset and effective learning of negation patterns.

---

## Conclusion

Given the substantial and consistent performance improvements, **future development will exclusively use BioBERT-based models**. DistilBERT (run_2) will be retained only as a lightweight baseline reference.

# Diagnosis of REAL_WORLD_CASES

inference with **Model:** `dmis-lab/biobert-base-cased-v1.1` (run_2)

> check notebook inference_test.ipynb for the outputs


🔴 Case: case_simple_single

*Problem*
Model over-extends entity:
  "large blister on"
  "toe"

*Potential Root cause*
  The model is labeling contextual tokens (large, on, toe) as symptoms. This is training signal: model might be absorbing modifiers and anatomical context into the symptom span


🔴 Case: case_negation

text: "The patient does not have muscle necrosis, only signs of muscle cramps."

- Model correctly detects negation for "muscle necrosis"
- But failed polarity flip after "only"

*This requires:*
- Either training data enrichment
- Or explicit negation scope modeling (something like scispacy)

🔴 Case: case_adjacent_entities

*Problem*
"facial edema rash" merged into one entity

*Potential Root Cause*
The model may have learned these often co-occur. The dataset will be checked to ensure if they actually co-occur (I did not recall so)

🔴 Case case_multiple_symptoms

Text: "The patient, male 65 years old reports hair shedding, blisters on his head, and knee pain.”


❌ "65" → SYMPTOM_POS
⚠️ "blisters on his head ," → SYMPTOM_POS (over-extended)

*Potential Insight*
"65" labeled as symptom is not overgeneralization of spans, it might be semantic misclassification.

Reason:
Numbers frequently appear inside symptom mentions in training data
(“2 days”, “5cm lesion”, “grade 3 pain”)
